# CMS 결함 수정 · 테스트 기반 · 첫 Supabase migration

## 변경 요약

- CMS 공개 버전 ID를 목록 길이 기반에서 최대 번호 이어받기(`nextVersionId`)로 바꿔 20개 슬라이스 이후 `v021` 중복 발급을 제거했다.
- 저장·자동 저장·공개·JSON 가져오기가 zod 검증 통과본(`result.data`)을 저장하도록 바꿔 trim 변환이 실제 저장본에 반영되게 했다.
- 스키마 필수 필드인 hero 슬라이드 `label`의 편집 UI 공백을 채웠다.
- 미디어 그리드가 렌더마다 `createObjectURL`을 재생성하던 것을 `useMediaLibrary`의 안정 URL 재사용으로 바꿔 깜빡임을 제거했다.
- 순수 로직을 `src/cms/site-utils.js`로 추출하고 vitest 단위 테스트 25건을 추가했다(`npm test`).
- `supabase/schema.sql` 초안을 삭제하고 배포 가능한 첫 migration(`supabase/migrations/20260802120000_init.sql`)으로 승격했다 — 불변 `site_releases`+`current_release_id` 포인터, 소유자 전용 `publish_site`/`rollback_site`, 낙관적 잠금 `save_draft`, 직접 쓰기 정책 제거(RPC 유일 경로), 문 수준 GRANT 명시.

## 변경 이유

Local MVP의 버전·검증·미디어 경로에 실제 결함이 있었고, 회귀를 막을 테스트가 0건이었다. 또한 초안 `schema.sql`이 스스로 표시한 공개 경계·불변 Release·충돌 처리 공백은 백엔드 MVP 착수 전에 DB 계약으로 확정할 필요가 있었다.

## 영향

- 20회 이상 공개해도 버전 ID가 유일하며 복원 대상이 모호해지지 않는다.
- 편집 UI에서 스키마의 모든 필수 필드를 수정할 수 있다.
- 다음 백엔드 MVP는 이 migration을 Supabase CLI 로컬 스택에 그대로 적용하는 것부터 시작한다. 초안 저장·공개·롤백의 클라이언트 계약은 `save_draft(expected_revision)`·`publish_site`·`rollback_site` RPC다.
- 워크스페이스, Storage 버킷/객체 RLS, 미디어 파생본·총용량 집계는 후속 migration 범위로 남는다.
- 02B 렌더러 화면·모션 동작은 변경하지 않았다(캐러셀 초기 인덱스 1은 정적 레퍼런스와 동일함을 확인).
